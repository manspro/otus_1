# Микросервисная архитектура - Миграция от монолита

Этот проект демонстрирует миграцию от монолитной архитектуры к микросервисной на примере dating-приложения.

## Архитектурная схема

```

│              (Web, Mobile, Desktop)                         │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│                    API GATEWAY                              │
│              (В продакшене - Nginx, Kong)                   │
└─────────────┬───────────────────────────┬───────────────────┘
              │                           │
              ▼                           ▼
┌─────────────────────────────┐  ┌─────────────────────────────┐
│        МОНОЛИТ              │  │    DIALOG-SERVICE           │
│     (Port 3000)             │  │     (Port 3001)             │
│                             │  │                             │
│ ✅ Аутентификация           │  │ ✅ Отправка сообщений       │

└─────────────────────────────┘  └─────────────────────────────┘
```

## Этапы миграции

### Этап 1: Анализ монолита ✅
- Изучение существующей кодовой базы
- Выявление границ доменов
- Определение зависимостей между модулями

### Этап 2: Выделение первого микросервиса ✅
- Выбор модуля диалогов как наименее связанного
- Создание отдельного NestJS приложения
- Реализация API диалогов в микросервисе

### Этап 3: Настройка инфраструктуры ✅
- Docker контейнеризация обоих сервисов
- Docker Compose для оркестрации
- Независимые базы данных

### Этап 4: Тестирование и документация ✅
- Postman коллекции для тестирования
- Swagger документация для каждого сервиса
- Сравнительное тестирование

### Этап 5: Следующие шаги (Планируется)
- API Gateway для маршрутизации
- Service Discovery
- Мониторинг и логирование
- Выделение других сервисов (Users, Posts)

## Запуск проекта

### Полная микросервисная архитектура
```bash
# Запуск всех сервисов
docker compose up -d

# Проверка статуса
docker compose ps

# Просмотр логов
docker compose logs -f
```

### Отдельные сервисы
```bash
# Только монолит
docker compose up dating-app-monolith -d

# Только dialog-service
docker compose up dialog-service -d
```

## Тестирование

### Swagger документация
- **Монолит**: http://localhost:3000/api
- **Dialog Service**: http://localhost:3001/api

### Postman коллекции
- `postman-collection.json` - Оригинальная коллекция для монолита
- `postman-collection-microservices.json` - Сравнительная коллекция

### Примеры запросов

#### Монолит (все функции)
```bash
# Регистрация пользователя
curl -X POST http://localhost:3000/user/register \
  -H "Content-Type: application/json" \
  -d '{"first_name":"John","second_name":"Doe","birthdate":"1990-01-01","biography":"Test user","city":"Moscow","password":"password123"}'

# Отправка сообщения
curl -X POST http://localhost:3000/dialog/user-id/send \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"text":"Hello from monolith!"}'
```

#### Dialog Service (только диалоги)
```bash
# Отправка сообщения
curl -X POST http://localhost:3001/dialog/user-id/send \
  -H "x-user-id: sender-id" \
  -H "Content-Type: application/json" \
  -d '{"text":"Hello from microservice!"}'

# Получение диалогов
curl -X GET http://localhost:3001/dialog/list \
  -H "x-user-id: user-id"
```

## Преимущества микросервисной архитектуры

### 1. Масштабируемость
- Независимое масштабирование каждого сервиса
- Оптимизация ресурсов под конкретные нагрузки

### 2. Технологическая свобода
- Разные технологии для разных сервисов
- Возможность экспериментов без влияния на всю систему

### 3. Изоляция отказов
- Проблемы в одном сервисе не влияют на другие
- Повышенная отказоустойчивость

### 4. Командная автономия
- Разные команды могут работать независимо
- Ускорение разработки и деплоя

### 5. Гибкость деплоя
- Независимые релизы
- Возможность отката отдельных сервисов

## Недостатки и сложности

### 1. Сетевые вызовы
- Латентность между сервисами
- Необходимость обработки сетевых ошибок

### 2. Консистентность данных
- Eventual consistency
- Distributed transactions

### 3. Операционная сложность
- Больше сервисов для мониторинга
- Сложность отладки распределенных систем

### 4. Тестирование
- Интеграционное тестирование сложнее
- Необходимость contract testing

## Метрики и мониторинг

### Текущие возможности
- Логи в консоль для каждого сервиса
- Health checks через HTTP endpoints
- Docker Compose статус мониторинг

### Планируемые улучшения
- Prometheus + Grafana для метрик
- ELK Stack для централизованного логирования
- Distributed tracing с Jaeger
- Service mesh (Istio)

## Заключение

Данный проект демонстрирует практический подход к миграции от монолита к микросервисам:

1. **Поэтапная миграция** - начинаем с одного сервиса
2. **Сохранение функциональности** - монолит продолжает работать
3. **Простота развертывания** - Docker Compose для легкого запуска
4. **Документированность** - подробная документация каждого шага

Это foundation для дальнейшего развития микросервисной архитектуры в зависимости от потребностей бизнеса.
